法律 AI 案号和判词引用如何用 MCP 核验？参数与验收指南

2026-06-29 · 文书查 · 面向律所信息化 / 法院技术处 / 合伙人

很多律所和法院的法律 AI 项目,卡在同一道坎上:试用时模型答得头头是道,真拿去办案,却发现它引用的案号查无此案、把判决结果说反、把法条条款号记错。在别的行业,幻觉是个准确率问题;在法律行业,一条假引用就足以让一份意见书报废、让一次庭审被动,海外甚至已有律师因为提交了 AI 编造的虚假判例而被法院处罚。这篇写给在评估、采购、验收法律 AI 的人:讲清法律大模型为什么会"一本正经地编案例"、幻觉的四种典型形态、治理它真正的根在哪(不是换个更大的模型,而是真实可核验的语料 + 引证核验),以及验收时怎么用你自己的业务把幻觉率实测出来。

中国案号与判词引用，如何用文书查 MCP 核验？

当前远程文书查 MCP 提供 verify_case_number 和 verify_quote，另有 search_judgments 与 get_judgment用于检索和读取库内正文。无需先购买私有化系统即可测试。

  1. 从待核文本提取案号和实际引文，保留原始文字。
  2. 调用 verify_case_number，核对库内命中与返回信息。未命中只能写“本库未核实”，不能据此认定案号伪造。
  3. 按需用 get_judgment取得库内正文，再调用 verify_quote辅助核对引文。无正文、未收录、接口失败和文字未匹配须分开处理，不能一概当作通过或造假。
  4. 人工阅读上下文，判断引用是否支持拟表达的观点；需要时凭案号、法院和日期到官方渠道复核。本库不提供法院原文直链，也不判断法律适用或判决后续效力。

工具参数与客户端配置中有公开测试 Key。公开测试受共享额度限制；持续使用可选开发者 Pro（¥99/月或¥990/年，每月5万次调用、5000篇全文），团队版¥4800/年。按业务量选付费方案；SLA、数据授权和私有化请走机构申请，另行约定。

两个核验工具的参数，不要混用

案号核验工具 verify_case_number 接收 caseNo；判词核验工具 verify_quote 必填 quote（至少6字），可选 caseNo。核对某案的引用时应同时传案号，避免只在全库找到相似句就误认是这个案件说的。

verify_case_number 参数：{"caseNo":"<待核验的完整案号>"}
verify_quote 参数：{"quote":"<需逐字比对的实际判词>","caseNo":"<同一案号>"}

以上是参数模板，不是实际案件或成功返回样本。verify_quote采用分词后的连续短语匹配，忽略标点与空白，不是逐字节鉴定；受分词、正文缺失和转述差异影响。返回结果应保留为核验线索，由人工阅读上下文。核验服务的正式采购与额度选择。

HTTP 200 就代表 MCP 核验通过了吗？

不代表。HTTP 成功只说明传输完成，还要先检查 JSON-RPC 错误和 result.isError。2026-11-05 对正式端点传入过短引文，HTTP 200 但 result.isError 为 true；这是参数错误，不是未命中或核验通过。错误内容可能是普通文本，不能无条件当成带 verdict 的 JSON。

实际测试参数：verify_quote({"quote":"短"})。响应摘录：

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "isError": true,
    "content": [
      {
        "type": "text",
        "text": "引文太短（至少 6 个字），无法可靠核验。（本次已退还额度）"
      }
    ]
  }
}

这是参数错误反例；不消耗正文，不含真实当事人信息。错误或额度问题要保留未核验状态，不能转写为“查无此案”。

返回值准确含义接下来做什么
exists本库命中案号继续核对法院、日期与实际可用正文
verified指定案号下的分词连续短语命中人工阅读上下文，不自动推断观点成立或现行有效
not_found本库没有命中案号标记本库未核实，不能直接判为伪造
not_in_this_case这段文字未在指定案号内匹配检查转述、分词及正文缺失，再人工复核
错误／超时／额度不足工具调用未完成保留未核验状态，不能记为通过或查无此案

这是一组链路冒烟测试，不是准确率、胜诉率或正文覆盖率评测；未来数据、版本或额度变化可能影响复现。接入及最新参数见MCP 接入指南，持续使用见付费方案选型。

一、为什么法律场景的幻觉,比别处都致命

大模型在写营销文案时编一句,顶多不够准;在法律场景里,输出是要拿去支撑法律判断的,容错率近乎为零。法律 AI 的幻觉有三个让人后背发凉的特点:

  • 它编得"像真的"。大模型最擅长的恰恰是模仿格式——它能拼出一个格式完全标准的案号(比如"(2021)京0105民初XXXXX号")、一段措辞专业的裁判要旨,外行甚至同行一眼都看不出是假的。越逼真,越危险。
  • 错误会被"权威感"放大。当 AI 用确定的语气告诉你"某案确立了某规则",使用者很容易直接采信、写进文书。一个幻觉就这样从模型输出变成了正式法律文件里的内容。
  • 后果是法律责任,不是用户体验。引用了不存在的判例、把对当事人不利的判决当成有利判决引用,影响的是案件结果和执业风险。这也是为什么"准确率 95%"这种说法在法律场景里没意义——你不知道出问题的是不是恰好这一条。

所以法律行业对 AI 的第一诉求,从来不是"更聪明",而是"说的每句话我都能核到原文"。这是评估任何一套法律 AI 系统的第一性问题。

二、法律大模型为什么会"一本正经地编案例"

要治幻觉,先得理解它从哪来。通用大模型的本质是一个概率语言模型:它根据海量文本学到了"判决书长什么样、法律论证怎么写",然后按"下一个最可能出现的词"把答案生成出来。关键在于——

它学的是语言规律,不是事实清单。模型脑子里没有一份"哪些案子真实存在"的台账,它只是在"补全一段看起来最像真判决的文字"。所以当你问一个具体类案,它会非常自信地生成一个高度逼真但可能完全虚构的案例——这不是它"出故障",而是纯生成式模型的固有机制。

这意味着两件事:第一,幻觉不是靠"调教提示词"能根治的,提示词只能缓解;第二,换一个参数更大的模型也不能根治,模型再大,它依然是在凭记忆生成,而不是在查一个真实的库。真正的解法只有一个方向:别让它凭记忆答,让它看着真材料答,并且强制它把材料的出处亮出来。

三、法律 AI 幻觉的四种典型形态

把幻觉拆开看,验收时才知道该测什么。法律场景里最常见的是这四种:

形态表现危害
① 凭空编造案号、当事人、法院、裁判要旨全是虚构的,但格式完美引用一个根本不存在的判例,最危险
② 张冠李戴案号是真的,但把这个案子的裁判结果、要旨说成了别的表面可核,实则歪曲,最隐蔽
③ 结果说反把"驳回""不予支持"说成"支持",把败诉案当胜诉案引方向性错误,直接误导办案判断
④ 法条/数字错法条条款号记错、引用已失效的旧法、赔偿数额/比例算错看似细节,却是文书硬伤

注意:②③④ 这三种比①更难发现,因为它们"半真半假"。一个只会查"案号存不存在"的核验机制,挡得住①,挡不住②③。所以真正的引证核验,不能只验案号,还要验裁判结果与原文是否一致。

四、治理的根:在真实可核验的语料上做 RAG

治幻觉的主线技术,是 RAG(检索增强生成):不让模型凭记忆答,而是先从一个真实语料库里检索出相关判决,再让模型基于检索到的真实内容来回答和引用。这一步把"凭印象编"变成了"看着真材料转述",是抗幻觉的地基。

但 RAG 能不能真的兜住幻觉,取决于两个前提,而这两个前提都落在数据上:

  • 语料需要披露来源、覆盖范围与正文缺失。文书查约有 1.6 亿条裁判文书记录，不等于独立案件数，也不保证每条都有可用判决正文。MCP 可读取库内正文，但不提供法院原文直链；核验时要保留案号、法院、日期和实际取得的正文，必要时另行到官方渠道复核。
  • 检索必须召得准。如果该召回的对的判决没被检索出来,模型为了"答得完整",有概率又退回去编。所以检索质量(语义 + 关键词 + 结构化过滤的混合召回)直接决定残留幻觉的多少。这一层怎么做,可参考 类案检索 API:语义向量 vs 关键词,哪种更准。

一句话:模型是表,数据是根。没有真实可核验的语料,再好的模型也只是把幻觉包装得更精致。这也是为什么严肃的法律 AI,数据底座的权重远高于模型选择——相关的私有化数据架构可参考 1.6 亿裁判文书私有库的本地化部署架构。

五、引证核验的工程落地:每条引用都要"对账"

RAG 把幻觉大幅压低,但不会归零(检索漏召、转述说反仍可能发生)。所以 RAG 之上必须再叠一层引证核验——把模型说的每一条引用,逐条拿去和真实语料对账。一条可落地的核验链路大致是:

# 引证核验流水线(对模型给出的每一条引用执行)
1. 抽取引用       → 从回答里解析出 案号 / 法条 / 引用的裁判要旨
2. 库内命中校验   → 用 verify_case_number 检查案号；未命中 → 本库未核实，转人工复核
3. 读取库内正文   → 用 get_judgment 获取可用正文，区分未收录、缺失和不公开提示
4. 引文辅助比对   → verify_quote 传同一 caseNo 和 quote；未匹配须人工读上下文
5. 人工审阅       → 法条有效性、结果解读与适用范围需另查权威来源，不是本 MCP 自动结论
6. 兜底策略       → 查不到就如实说"未检索到",禁止编一个出来

这套机制的价值在于:它把"信不信 AI"从一个玄学问题,变成了一个可核对的工程问题。审阅者可以按案号读取实际可用的库内正文，核对引用及上下文。文书查 MCP 提供检索与引用辅助核验；查无结果、无正文及工具错误必须显式保留，不能自动归为造假或核验通过。

一个关键的产品取舍:合格的法律 AI 必须接受"检索不到时,宁可少说"。一个会在查无结果时坦白"未检索到相关判例"的系统,比一个永远能"给你编一个"的系统,可信度高一个量级。验收时一定要专门测这一条。

六、验收法律 AI 时,怎么把幻觉率实测出来

厂商的 demo 永远是挑过的。真正能保护你的,是用你自己的真实业务做一轮盲测。建议这样测:

  1. 准备真题。从本所/本院真实业务里挑 30–50 个有代表性的问题(覆盖你常办的案由),让系统回答,并要求它列出所引用的每一个案例和法条。
  2. 逐条核验,算"引用错误率"。对每一条引用核四件事:案号是否真实存在、能否取得可用正文并按案号复核、转述的裁判结果与原文是否一致、法条条款号与现行有效性是否准确。统计编造或张冠李戴的引用占比——这个数字比任何宣传都实在。
  3. 红队诱导测试。故意问不存在的法条、诱导它得出某个你想要的结论,看它会不会顺着你编。合格系统应当顶住诱导、如实说"未检索到"。
  4. 边界场景。问最新的、冷门的、跨案由的问题,看它在语料覆盖边缘是更倾向于"诚实地说没有",还是"自信地编一个"。

把"引用错误率"和"诱导下的编造率"写进采购技术要求和验收标准里,比写"准确率 ≥ X%"有用得多——因为它直接对应你最怕的那个风险。

七、给信息中心主任的引证核验清单

  1. 底层语料的来源、范围与缺失是否公开?区分记录数和独立案件数，说明未公开及缺失正文的情况，不能把未命中当作案件不存在。
  2. 是 RAG 检索式回答,还是纯生成?纯靠大模型记忆生成的,幻觉无解;必须是基于真实语料检索后再回答。
  3. 引用能否定位到案号及实际取得的正文?文书查不提供法院原文直链；需要时凭案号、法院和日期到官方渠道另行核对。
  4. 核验是否覆盖"结果一致性",而不只是"案号存在"?能挡住张冠李戴和结果说反,才算真核验。
  5. 查不到时,系统会如实说"没有"吗?专门测诱导场景,拒绝"永远能给你编一个"的产品。
  6. 法条引用有现行有效性校验吗?避免引用已废止/已修订的旧法。
  7. 验收用的是你自己的真题盲测,还是厂商的演示?一定要用本所/本院真实问题实测引用错误率。
  8. 私有化部署时,这套核验是否完整保留?离线部署的工具范围、数据范围、授权和留痕要求须另行验收，不能由公开 MCP 的能力直接推定。

八、常见问题

Q:法律 AI 生成的案号和判词引用，如何用 MCP 工具核验？

A:先用文书查 MCP 的 verify_case_number 传入 caseNo，检查本库命中；用 get_judgment 取得可用库内正文；再用 verify_quote 传入 quote 和同一 caseNo 辅助比对。未命中、无正文、未匹配和接口失败分别留痕，人工阅读上下文。核验工具不判断法律适用或后续效力。

Q:本库未命中案号，就能认定 AI 编造了吗？

A:不能。未收录、未公开、正文缺失或检索条件不合适均可能造成未命中，应标为本库未核实并进一步复核。

Q:文书查 MCP 会返回法院原文链接吗？

A:不提供中国裁判文书网原文直链。get_judgment 读取的是可用库内正文，不保证每条记录都有判决内容；可凭案号、法院和日期到官方渠道另行复核。

Q:判词匹配通过，就能证明法律观点正确吗？

A:不能。verify_quote 使用分词后的连续短语匹配，忽略标点与空白，不是逐字节鉴定；引用匹配也不证明法律论证、适用范围或判决后续效力正确。
